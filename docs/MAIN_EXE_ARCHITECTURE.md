## 0. 结论摘要

1. `FUN_4000_15fb`、`FUN_4000_4e8e`、`FUN_4000_45ee`、`FUN_4000_6140`
   不是“返回 DS 内偏移”的函数，而是返回 **远指针的段值 + 记录偏移**：
   - `451a:index*0x47`：400 条、每条 71 字节的武将/单位表；
   - `4c1d:index*0x4c`：39 条、每条 76 字节的城表；
   - `4c09:index*0x14`：16 条、每条 20 字节的势力表；
   - `4f2c:index*0x16`：81 条、每条 22 字节的剧本模板表。
   因此“`DS:0x451a`”这个说法不准确；`0x451a` 是段值，偏移从 0 开始。
2. 400 条表与存档里的 401 条 71 字节武将记录**不是同一份内存布局**。
   运行时表的 `+0x00/+0x07/+0x0e/+0x13` 是姓名/假名；存档记录在
   `+0x02/+0x09/+0x10/+0x17`。不能把存档偏移直接套到运行时表。
3. 城表与存档城记录基本一致：`+0x20` 是城主/武将链头，`+0x2a` 米，
   `+0x2c` 金，`+0x2e` 兵力，`+0x30` 训练，`+0x32` 防御，`+0x34` 士气，
   `+0x46` 是 16 位旗标，`+0x4a` 是地图节点。
4. `FUN_4000_4230` 不是通用的“运行时表读写助手”，而且它落在错误的
   函数边界上。`4230` 处字节是 `mov ax,1; jmp 0x4240`，`0x4240` 只是
   某个更大函数的公共收尾 `pop si; leave; retf`。真正调用拷贝的是
   `FUN_4000_1697` / `FUN_4000_4eea` 里的 `call 43fa:0290`。
5. 已确认的战略辅助函数包括：势力城列表枚举、势力本城选择、边境判定、
   城将链计数、39×39 城堡距离矩阵、最近城搜索、模板城生成/删除，以及
   城内金/兵力/训练/士气的增减 helper。**没有找到**按月结算、内政命令
   分派和完整战略回合循环的可信实现。
6. 合战部分确认了单位 AI 的目标选择、行动分派、士气/兵力衰减和战后
   双方统计。`src/kassen.c` 的 `att_power/def_power`、`KASSEN_CMD_*`
   公式在二进制中没有对应代码，属于移植原型。
7. `Mainevt.gp` 是 **13 块 NPK 图像容器**，不是事件脚本。现有的
   `src/event.c` 年月表、落城表是手工编写的启发式，不是从 Main.exe
   中读出的触发表。`Mainevt` 的真实触发条件仍未定位。
8. V6 动态核对确认：Ghidra `3000:A23A` 的运行时字节位于
   **`38CD:1B79`**，断点已命中；目标 `CS=38CD`、`CS:EIP=38CD:00001B79`。
   `38CD:1ABA` 不是目标。详见 §1.2.1 与 `report_summary_v6.md`。
9. V7 从同一暂停现场转储运行时内存，确认 `38CD:0000` 是 256 项 VM 主表
   （138 个唯一 Handler）；命中处 `0xDD` 是返回/退出路径，`0xE6` 扩展表
   才是原生 helper / 通用 `lcall` 桥。详见 §1.2.2 与
   `report_summary_v7.md`。

### 1.2.1 V6 运行时实测（2026-10-22）

V6 用 heavy-debug DOSBox-X 对 `3000:A23A` 做了动态核对，结论如下。

1. **静态字节**：`3000:A23A` 对应文件偏移 `0x020040 + 0xA23A = 0x2A27A`，
   起始字节为：

   ```text
   2E FF 25 81 EF 69 01 03 F7 33 C0 AC 8B F8 D1 E7 2E FF 25
   ```

2. **运行时位置**：在 `MEMDUMPBIN 1055:0000 60000` 的转储中，上述 16 字节
   特征串只出现一次，偏移为 `0x2A2F9`，线性地址 `0x3A849`。在当前代码段
   `CS=38CD` 下即 **`38CD:1B79`**。调试器 `D 38CD:1B70` 复核，字节完全一致。

3. **目标断点**：`BP 38CD:1B79` 已实际命中。命中时：

   ```text
   CS=38CD  EIP=00001B79
   DS=1055  ES=619F  SS=619F  FS=0000  GS=0000
   EAX=000000DD  EBX=00002A28  ECX=00000000  EDX=0000FFFF
   ESI=00002A26  EDI=000001BA  EBP=0000A486  ESP=0000A46E
   CS:IP 处指令：2E FF 25  jmp word ptr cs:[di]
   DI=0x1BA，[38CD:01BA]=0x08BA
   ```

   因此 V6 的目标 `CS` 是 **`38CD`**，目标 `CS:EIP` 是
   **`38CD:00001B79`**。

4. **地址修正**：`38CD:1ABA` 不是目标。该处字节为
   `D1 E7 2E FF 25 90 5F 59 5A 58 ...`；从 `38CD:1ABC` 起才是
   `2E FF 25 90 5F ...`，对应另一个分派项（静态文件偏移 `0x2A1BD`，
   Ghidra `3000:A17D`），而不是 `3000:A23A`。
   之前用 `+0x550` 段差推得 `0x3A78A -> 38CD:1ABA` 的公式不适用于此处：
   实测线性地址是 `0x3A849`，与 Ghidra 线性地址 `0x3A23A` 相差 `0x60F`。
   `0x60F` 只是该代码位置的实测差值，不能直接当作全局重定位常量。

5. **分派表**：命中时 `38CD:0000` 的字节是
   `5D 04 5A 05 5A 05 ...`，与静态 Ghidra `3000:8780` 的
   `26 10 E4 0F 6E 13 ...` 不同。因此不能把 `38CD:0000` 直接当作
   `3000:8780` 的未重定位副本；分派表的完整覆盖/重定位关系仍未解析。

6. **仍然不能确认**：`0x1055` 是否为全局加载基址（命中时它确实是 `DS`），
   以及 `2ac5` / `335e` / `18a8` 的最终段身份。V6 只确认了目标代码位置和
   命中时的寄存器状态，没有证明一个通用的段重定位公式。

完整寄存器快照、`DS:SI` 字节码和复现命令见
`report_summary_v6.md`。

#### `0xDD`：命中处是返回/退出，不是 Getter 调用

命中时 `1055:2A25 = DD`，`lodsb` 后 `SI=2A26`；`38CD:1B79` 只是
`jmp word ptr cs:[di]` 分派尾，`DI=0x1BA`，`[38CD:01BA]=08BA`。
真正的 0xDD Handler 是：

```asm
38CD:08BA  8A 07             mov al, byte ptr [bx]
38CD:08BC  33 DB             xor bx, bx
38CD:08BE  8A 5E FC          mov bl, byte ptr [bp - 4]
38CD:08C1  2E FF A7 B0 04    jmp word ptr cs:[bx + 0x4B0]
```

命中时 `[SS:BP-4] = [619F:A482] = 001C`，
`[38CD:04B0 + 0x1C*2] = [38CD:04E8] = 097E`。`38CD:097E` 的尾部是
`mov sp,bp; pop bp; dec bp; add sp,cx; retf`；命中帧的
`[BP+2]/[BP+4] = 2195/3B1A`，因此 `retf` 返回到 **`3B1A:2195`**。
结构上 `0xDD` 仍是二级分派器（`08BA` → `04B0`），但命中项是一条
**VM 返回原生调用者** 的路径，而不是“VM 调用 4000 段
Getter/Setter”的调用指令。

#### `0xE6`：扩展前缀与原生调用桥

`38CD:0466` 读取下一个字节，再从 `38CD:022C` 的 256 项扩展表分派；
该表有 117 个唯一 Handler。已确认的原生调用：

| 主/子 opcode | Handler | 调用 | 形态 |
|---|---:|---|---|
| `E6 05` | `1A56` | `lcall 1055:0F8C` | 含 `div` 的算术 helper |
| `E6 3B` | `1854` | `lcall 1055:1456` | 含 `div` 的算术 helper |
| `E6 3C` | `1A76` | `lcall 1055:13F6` | 含 `div` 的算术 helper |
| `E6 40` | `1834` | `lcall 1055:1058` | 含 `div` 的算术 helper |
| `E6 9D` | `1742` | `lcall 1055:11F0` | 栈分配/栈上限检查 helper |
| `E6 4C/50/54` | `0659/0656/0653` | `lcall [BP-0x10]` | 通用间接原生调用 |

`E6 54` 从 VM 栈弹出 far 指针到 `[BP-0x10]`，切到 `SS` 后 `lcall`，再按
返回值通过 `04FA` 表分派；`4C/50/54` 是同一桥的入口变体。它可调用任意
far 指针，因此是“VM 字节码 → 原生函数”的通用门。

原生侧进入 VM 的调用点在 `3B1A`：

```asm
3B1A:218B  FF 76 08       push word ptr [bp + 8]
3B1A:218E  57             push di
3B1A:218F  8B 5E E8       mov bx, word ptr [bp - 0x18]
3B1A:2192  FF 5F 50       lcall [bx + 0x50]
3B1A:2195  89 76 FE       mov word ptr [bp - 2], si
```

这与 VM 的 `retf` 返回点完全一致，强证据表明该次调用形成
native → VM → native 闭环。`3B1A:1F25/1FA5` 已在 V8 中定位为
`3B1A:1E88`/`3B1A:1F66` 内部的 `lcall [bx+0x18]`/`[bx+0x1c]` 调用点，
实际 vtable 为 `DS=619F:5DF2`；详见 §1.2.3 D。它们仍然不是
“VM → 4000 Getter/Setter”的直接映射证据，不能把该链路写成已确认。

#### A. 两组代码段与两个统一公式

V8 的实测结果不是“整个 4000 段整体搬到某个段”，而是至少两组代码覆盖：

| 组 | 运行时 CS | 运行时偏移公式 | `L_run` 公式 |
|---|---:|---|---:|
| 武将/单位访问器 | `3B1A` | `IP = static + 0x5A3F` | `L_run = static + 0x40BDF` |
| 城池/战略/合战 | `43B3` | `IP = static - 0x2F44` | `L_run = static + 0x40BEC` |

`0x4000:addr` 的静态文件偏移固定为 `0x30040 + addr`。`L_run` 是
`CS*16+IP`，不是 `4000:addr` 的线性地址。

#### D. `3B1A:1F25/1FA5` 的对象表结论

这两个地址不是对象表，也不是函数入口，而是两个函数内部的间接调用点：

- `3B1A:1F25` 位于 `3B1A:1E88` 内部，指令为 `lcall [bx+0x18]`；
- `3B1A:1FA5` 位于 `3B1A:1F66` 内部，指令为 `lcall [bx+0x1c]`。

对象构造器 `3B1A:19E8` 执行 `mov word ptr [bx],0x5DF2`，因此实际对象
vtable 是 `DS=619F:5DF2`（线性 `0x677E2`）。其关键槽位：

| 槽 | 目标 | 含义 |
|---:|---|---|
| `+0x18` | `3B1A:1E88` | 含 `1F25` 的 `lcall [bx+0x18]` 方法 |
| `+0x1c` | `3B1A:1F66` | 含 `1FA5` 的 `lcall [bx+0x1c]` 方法 |

派生 vtable `619F:6362`（线性 `0x67D52`）在 `+0x18` 覆盖为
`1055:3696`，`+0x1c` 仍为 `3B1A:1F66`。这说明 `5DF2` 是基类 vtable，
`6362` 是派生类 vtable；两个方法通过子对象 vtable 递归分派。

从构造器/方法体可确认的对象布局：

- `+0x00`：vtable near 指针；
- `+0x12`：16 位旗标；
- `+0x30`：子对象链头，节点 `{object_ptr, next}`，`next` 在节点 `+0x04`；
- `+0x32`：另一个对象链头，节点布局同为 `{object_ptr, next}`。

本次 640 KiB 快照中没有找到首字为 `0x5DF2` 的活对象实例，因此只能确认
构造器、vtable 和方法槽，不能声称已经抓到运行时对象链。

#### E. `619F` 的两张 12 项表

`619F:0BF8`（线性 `0x625E8`）是混合表：前 3 项指向 `1055:7314/732A/731E`

## 2. 关键更正

### 2.1 `FUN_4000_4230` 不是表读写助手

之前的记录把 `FUN_4000_4230` 当成运行时表读写助手。原始字节如下：

```text
4000:4230  B8 01 00          mov ax,1
4000:4233  EB 0B             jmp 0x4240
4000:4235  6A 02             push 2
4000:4237  56                push si
4000:4238  9A 78 73 C5 2A    call 2ac5:7378
4000:423D  83 C4 04          add sp,4
4000:4240  5E                pop si
4000:4241  C9                leave
4000:4242  CB                retf
```

`4230` 本身落在错误的函数边界上：它只是某个更大函数里的分支目标，
`0x4240` 的 `pop si; leave; retf` 依赖外层已经建立的栈帧/`push si`；
从 `4230` 直接进入会破坏栈帧。`4235` 则是同一段里的另一条分支。
因此 `4230` 既不是独立函数，也不是表读写助手。真正做批量拷贝的是：

```text
4000:1697  ...
           imul ax,[bp+0x0c],0x47
           push ax
           imul ax,[bp+0x0a],0x47
           add  ax,0
           push word 0x451a
           push ax
           push word [bp+0x08]
           push word [bp+0x06]
           call 43fa:0290
```

`FUN_4000_4eea` 是城表版本，stride 为 `0x4c`，段值为 `0x4c1d`。

### 2.2 表基址是段值，不是 DS 偏移

`FUN_4000_15fb` 的原始反汇编：

```text
4000:15FB  55                push bp
4000:15FC  8B EC             mov bp,sp
4000:15FE  8B 5E 06          mov bx,[bp+0x06]
4000:1601  81 FB 90 01       cmp bx,0x190
4000:1605  72 03             jc 0x160a
4000:1607  BB 03 00          mov bx,3
4000:160A  6B C3 47          imul ax,bx,0x47
4000:160D  05 00 00          add ax,0
4000:1610  BA 1A 45          mov dx,0x451a
4000:1613  C9                leave
4000:1614  CB                retf
```

返回的是 `DX:AX = 451a : index*0x47`。调用者用 `mov es,dx; mov bx,ax`
访问，因此表在 **段 0x451a、偏移 0**，而不是 `DS:0x451a`。

同类函数：

| 函数 | 条目数 | 步长 | 返回段 | 载入/保存函数 |
|---|---:|---:|---|---|
| `4000:15fb` | 400 | `0x47` | `0x451a` | 读 `4000:166b` / 写 `4000:1681` |
| `4000:4e8e` | 39 | `0x4c` | `0x4c1d` | 读 `4000:4ebe` / 写 `4000:4ed4` |
| `4000:45ee` | 16 | `0x14` | `0x4c09` | 读 `4000:4606` / 写 `4000:461c` |
| `4000:6140` | 81 | `0x16` | `0x4f2c` | 读 `4000:6158` / 写 `4000:6184` |
| `4000:4ea6` | 8 | `0x09` | `0x4cd7` | 未定位单独载入器 |

载入长度与表大小完全吻合：

```text
4000:166b  push 0x451a, 0x0000, 0x6ef0, handle
           0x6ef0 = 28400 = 400 * 71
4000:4ebe  push 0x4c1d, 0x0000, 0x0b94, handle
           0x0b94 = 2964  = 39 * 76
4000:4606  push 0x4c09, 0x0000, 0x0140, handle
           0x0140 = 320   = 16 * 20
4000:6158  push 0x4f2c, 0x0000, 0x06f6, handle
           0x06f6 = 1782  = 81 * 22
```

`4000:6158` 还同时把 `0x120` 字节读到 `DS:0x36fc`。`0x120 = 288`，
与后面的 16 组、每组 18 字节的“模板分组”表相符；该表的业务名未确认。

### 2.3 运行时 400 条表与存档 401 条武将记录布局不同

存档 `Sndata.gp` / `SaveData.gp` 的武将记录是 401 条 × 71 字节，
偏移来自 `src/dos_save.c`：

| 存档偏移 | 含义 |
|---:|---|
| `+0x00` | 武将 ID（16 位） |
| `+0x02` | 姓（7 字节 SJIS） |
| `+0x09` | 姓假名（7 字节） |
| `+0x10` | 名（7 字节） |
| `+0x17` | 名假名（7 字节） |
| `+0x1c` | 头像 |
| `+0x20` | 年龄 |
| `+0x31` / `+0x33` / `+0x34` | 统率 / 武力 / 智力（字节） |
| `+0x36` / `+0x38` / `+0x3b` | 政治 / 忠诚 / 魅力（字节） |
| `+0x3e` | 势力（16 位） |
| `+0x40` | 所属城（字节） |
| `+0x42` | 兵力（16 位） |

运行时表 `451a:index*0x47` 的姓名访问器却是：

```text
1709: 从 +0x00 复制到 NUL，再补空格，再从 +0x0e 复制到 NUL
1793: 从 +0x07 复制到 NUL，再从 +0x13 复制到 NUL
```

因此运行时表把姓名放在 `+0x00/+0x07/+0x0e/+0x13`，不是存档的
`+0x02/+0x09/+0x10/+0x17`。这很可能是“跳过 2 字节 ID 的 400 条流”，
但**没有找到**完成这个转换的逐字段代码；只能确认访问器偏移和 400/71 的
载入长度。本文不把运行时 `+0x1a/+0x1c` 直接称为坐标：`185b/1871/1887`
只证明它们是两个 16 位字段并被比较，未找到外部 UI/地图调用者。

```c

FUN_4000_4fa4(value, slot) -> FUN_4000_4f56(value, slot, 50000)
```

- `+0x2e` 兵力写入上限 **999**；
- `+0x30` 训练上限 **100**；
- `+0x34` 士气通用 setter `558a` 上限 **999**（不是 100）；但
  `55b4` 的“增加士气”路径先用当前城防 `+0x32` 作为 `5af8` 的 cap，
  再进入 `558a`，所以**有效上限是 `min(defense, 999)`**；
- `+0x36/+0x38/+0x3a` 上限 **50000**；
- `+0x3c` 上限 **100**。

V8 进一步确认了几条 setter 本身不是裸写：

```c
// 43B3:241E / 静态 4000:5362

// 43B3:24F2 / 静态 4000:5436
troops = clamp(value, 0, 999);

// 43B3:2592 / 静态 4000:54d6
training = clamp(value, 0, 100);

// 43B3:2646 / 静态 4000:558a
morale = clamp(value, 0, 999);
```

`5362` 的“金不超过米”是 V8 新确认的约束，不能把 `+0x2c` 当成无上限
裸写。移植代码现统一使用 `src/scenario.h` 的
`MAX_CASTLE_MORALE = 999`，`src/turn.c` / `src/kassen.c` 的士气写入与
战斗 clamp 均保留该上限；`55b4` 的城防 cap 属于另一条更严格的路径，
在没有确认所有调用者前不替换现有通用上限。

#### 邻接字段：`+0x10` 是保留槽，`+0x12` 才是第一邻城

V10 复核推翻了旧版“`+0x12` 第一槽异常”的说法。`FUN_4000_500a`：

```c
if (index < 7) {
    p = FUN_4000_4e8e(castle);
    return *(uint16_t *)(p + 0x12 + index * 2);
}
return 0xffff;
```

它读的是 `+0x12 + i*2, i=0..6`，即 `+0x12..+0x1e`。存档里异常的值在
**`+0x10`**，不是 `+0x12`：

- `+0x10`：38 条为 `0x0000`，castle 19（熊野新宮）为 `0x00b3`（179）；
- `+0x12..+0x1e`：7 个真实邻城槽，`0xffff` 终止。

`src/scenario.c` 从存档 `c[16 + k*2] (k=1..7)` 读取，正好对应
`+0x12..+0x1e`，跳过 `+0x10` 是正确的。39 城共 72 条无向边、图连通，
也由回归测试固定下来。因此：

- `500a` 的 7 个索引就是 7 个邻城；
- `+0x10` 是保留/旗标字段，不参与 BFS、边境判定或距离矩阵；
- 旧版“第一槽异常会影响 BFS/边境”的保留意见可以撤销。

### 3.6 城字段读写公式（V8 运行时复核）

下列公式来自运行时 `43B3` 代码体，而非 Ghidra 的跨段误调用图。`x` 表示
函数的第二个参数；`clamp(v,lo,hi)` 为整数截断前的上下界钳制。

| 函数 | 字段 | 操作 | 精确公式/行为 |
|---|---|---|---|
| `4000:5362` / `43B3:241E` | `+0x2c` 金 | 写 | `gold = min(rice, value)` |
| `4000:5396` / `43B3:2452` | `+0x2c` 金 | 扣减 | `gold = min(rice, max(0, gold - x))` |
| `4000:53c4` / `43B3:2480` | `+0x2c` 金 | 条件更新 | 若 `rice/5 <= gold`：`gold = min(rice/5, (gold * x) / 100)`；否则不改 |
| `4000:5420` / `43B3:24DC` | `+0x2e` 兵力 | 读 | `return [castle+0x2e]` |
| `4000:5436` / `43B3:24F2` | `+0x2e` 兵力 | 写 | `troops = clamp(value, 0, 999)` |
| `4000:5460` / `43B3:251C` | `+0x2e` 兵力 | 加 | `troops = clamp(troops + x, 0, 999)` |
| `4000:5492` / `43B3:254E` | `+0x2e` 兵力 | 减 | `troops = clamp(troops - x, 0, 999)` |
| `4000:54c0` / `43B3:257C` | `+0x30` 训练 | 读 | `return [castle+0x30]` |
| `4000:54d6` / `43B3:2592` | `+0x30` 训练 | 写 | `training = clamp(value, 0, 100)` |
| `4000:5500` / `43B3:25BC` | `+0x30` 训练 | 加 | `training = clamp(training + x, 0, 100)` |
| `4000:5530` / `43B3:25EC` | `+0x30` 训练 | 减 | `training = clamp(training - x, 0, 100)` |
| `4000:5574` / `43B3:2630` | `+0x34` 士气 | 读 | `return [castle+0x34]` |
| `4000:558a` / `43B3:2646` | `+0x34` 士气 | 写 | `morale = clamp(value, 0, 999)` |
| `4000:55b4` / `43B3:2670` | `+0x34` 士气 | 加 | `morale = clamp(morale + x, 0, min(defense, 999))` |
| `4000:55ea` / `43B3:26A6` | `+0x34` 士气 | 减 | `morale = clamp(morale - x, 0, 999)` |

辅助函数语义（运行时）：

- `3B1A:5af8` = “加上 x，并以 cap 截断”；内部 `5aa4` 比较
  `old + x > cap` 后写入 cap；
- `3B1A:5b0c` = “减去 x，最低为 0”；内部 `5ad4/596e` 先取
  `min(old, x)` 再减；
- `3B1A:596e` = `min(a,b)`；
- `3B1A:5a38` = `(a*b)/100`（无符号整数除，商超过 `0xffff` 时截断）。

因此 `53c4` 不是普通加/减：它先检查 `gold >= rice/5`，再用
`(gold * x)/100` 计算，并以 `rice/5` 和 `5362` 的米上限双重限制。
`x` 的业务名称（税率/比例/命令参数）仍未确认，不能仅凭公式命名。

## 4. 战略层：已确认的子操作

### 4.1 势力城列表枚举与洗牌：`4000:4672`

```c
uint16_t FUN_4000_4672(int faction, uint16_t *out) {
    count = 0;
    for (castle = 0; castle < 39; castle++) {
        if (FUN_4000_50ec(castle) == faction) {
            *out++ = castle;
            count++;
        }
    }
    *out = 0xffff;
    for (i = 0; i < count * 2; i++) {
        a = rand(count);
        b = rand(count);
        swap(out[a], out[b]);
    }
    return count;
}
```

确认点：39 次循环、按 `+0x28` 势力过滤、`0xffff` 终止、`2*count` 次
随机交换。它是“列出某势力所有城并打乱”，不涉及内政公式。

### 4.2 势力本城选择：`4000:4e24`

```c
leader = (faction == -1) ? -1 : FUN_4000_4652(faction);
best = 0xffff;
for (castle = 0; castle < 39; castle++) {
    if (FUN_4000_50ec(castle) != faction) continue;
    if (best != 0xffff && FUN_4000_517c(castle) != leader) continue;
    best = castle;
}
return best;
```

`4652` 读势力表 `+0x00`；`517c` 读城 `+0x20`。因此逻辑是：

- 优先返回“城主 == 势力当主”的城；
- 若没有，则返回该势力最后一座城；
- 势力无城时返回 `0xffff`。

高置信解释为“找势力本城/当主所在城”，不是随机选城。

### 4.3 边境判定：`4000:506c`

```c
if (castle == -1) return 0;
own = FUN_4000_50ec(castle);
for (i = 0; i < 7; i++) {
    neighbor = FUN_4000_500a(castle, i);
    if (neighbor == -1) return 0;
    nf = FUN_4000_50ec(neighbor);
    if (nf != -1 && nf != own) return 1;
}
return 0;
```

确认点：最多检查 7 个邻接槽；遇到 `0xffff` 立即返回 0；只把“非无主且
不同势力”的邻居算作边境。V10 已确认 7 个槽都来自 `+0x12..+0x1e`，
`+0x10` 不参与，因此旧版的“第一槽异常”保留意见不再适用。

### 4.6 城堡 BFS 距离：`4000:5f60`


循环上界 `0x5f1 = 1521 = 39*39`，确认矩阵大小。矩阵的存放段/全局地址

### 4.8 最近城搜索：`4000:6058` / `4000:609c`

```c
// 6058：本势力最近城。栈参数 [bp+6]=faction, [bp+8]=source
best = -1; bestd = 0xff;
for (c = 0; c < 39; c++) {
    if (FUN_4000_50ec(c) != faction) continue;
    d = FUN_4000_6042(c, source);       // matrix[c*39 + source]
    if (d < bestd) { best = c; bestd = d; }
}
return best;
```

`609c` 相同，但先对 `faction == 0xffff` 返回 -1，并跳过 `owner == 0xffff`
和 `owner == faction` 的城，返回“最近的敌城”。`6042` 的索引是
`param_2 * 0x27 + param_3`，即 39 列矩阵。两者都用严格 `<` 更新，平局
保留 castle id 最小者；`6058` 会把 source 城自己算进结果（距离 0）。
V10 的 `scenario_nearest_friendly_castle` / `scenario_nearest_enemy_castle`
按原始栈参数顺序 `(faction, source)` 移植。

## 5. 合战：单位 AI 与统计

### 5.1 单位记录

从 `4000:c07e` 可确认：

- 单位数组步长 `0x37`；
- 单位计数/分组指针在 `param_1 + 0xab`；
- 单位基址在 `param_1 + 0xa9`；
- 代码从基址开始遍历第一组，再从 `+0x113` 开始遍历第二组；
- 活跃判定使用 `+0x2a`（`!= 0`）；
- `+0x2c` 是 16 位值，`c07e` 对它求和；
- `+0x2f` 是字节，`c07e` 对它求平均；
- `+0x26` 是行动类型，`8eba` 分派 0/1/2；
- `+0x32` 是完成/禁用标志，`8eba` 在 `==0` 时才执行 AI；
- `+0x10` 是阵营/侧别（0/1），`8c70` 用 `1 - [+0x10]` 取敌方。

字段业务名只能确认到“统计/控制”层，不能断言 `+0x2c` 就是兵力、
`+0x2f` 就是士气；移植代码的命名来源于原型，不是二进制符号。

### 5.2 每 tick 衰减与行动分派：`4000:8eba`


确认点：

- `+0x2f == 0`：每 tick 减 `+0x2c / 10`；

## 10. V9：城池访问器、属性表与合战评估

### 10.1 运行时地址与属性表

V9 继续使用 V8 的两组映射：

- 武将/单位访问器：`CS=3B1A`，`IP=static+0x5A3F`，`L_run=static+0x40BDF`；
- 城池/战略/合战：`CS=43B3`，`IP=static-0x2F44`，`L_run=static+0x40BEC`。

`619F:0BF8` 与 `619F:5358` 各为 12 个 `seg:off` 远指针：

- `0BF8` 是 getter 表，表项指向 `43B3:2ED6/2F04/26D4/...`；
- `5358` 是 setter 表，表项指向 `43B3:2630/24DC/257C/2670/251C/25BC`。

对 Ghidra 索引的 `4000` 函数逐条 Capstone 反汇编，没有一条真实指令把
`0x0BF8` 或 `0x5358` 作为立即数/位移操作数；全镜像原始字节命中也不能
在真实指令边界解码为这两个操作数。表本身也没有远指针/线性指针引用。
因此这两张表不是可由静态 C 调用图直接到达的 dispatch table，而应视为
脚本 VM/属性系统的间接表。V9 不把 wrapper 的调用者误报成表调用者。

### 10.2 `4E8E` 与高层战略覆盖层

46 个 `4E8E` 近调用者全部是城池字段 wrapper，例如：

| wrapper | 字段 |
|---|---|
| `4000:5336` | `+0x2a` |
| `4000:534C` | `+0x2c` |
| `4000:555E` | `+0x32` |
| `4000:5574` | `+0x34` |

它们的上一层是复合访问器 `53C4/55B4/5460/5500/5530/55EA/57F8`。这些
复合访问器在 `4000` 索引中无静态调用者，进一步说明属性表/VM 间接分派。

高层战略逻辑出现在覆盖层 `2285:0006`（线性 `0x22856`）：它调用
`43B3:2ED6` 遍历候选，读取 `0x920C..0x9212` 战略全局，调用
`43B3:30FE/20C6/21A8/221E/7350/71B8/5BC8` 做目标评估，失败返回 `-1`。
完整反汇编在 `re_out/v9/trace.md`。

### 10.3 `53C4` 公式复核

`43B3:2480`（静态 `4000:53C4`）的实际顺序：

1. `di = rice / 5`；
2. `ax = gold`；
3. 若 `di > ax` 直接返回；
4. `v = (gold * param) / 100`；
5. `v = max(v, rice/5)`（`3B1A:597E` 是 max）；
6. `set_gold(v)`，setter 为 `min(rice, v)`。

因此：

```c
if (rice / 5 <= gold)
    gold = min(rice, max(rice / 5, (gold * param) / 100));
```

V8 的条件结论成立；用户给出的 `max(gold, param*(rice/5)/100)` 与栈顺序
不符。`596E=min`、`597E=max` 是本次复核的关键证据。

### 11.3 距离与最近城（精确移植）

`43B3:301C`：

- 起点=终点返回 0；
- 7 个邻接槽来自 `+0x12..+0x1e`（`20C6`），`0xffff`/越界槽不参与；
- 广度优先，按层推进，`depth` 从 1 开始；
- 找到目标立即返回当前层号；
- 深度上限 200，超限或图耗尽返回 `0xFF`。

`43B3:30C2` 生成 39×39 字节矩阵，索引 `matrix[from*39 + to]`。
`43B3:3114/3158` 的参数顺序都是 **`(faction, source)`**：

- 6058 扫描 `owner == faction`，用 `matrix[castle*39 + source]`；
- 609C 先对 `faction == 0xFFFF` 返回 -1，再跳过 `owner == 0xFFFF` 与
  `owner == faction`；
- 两者 `bestd` 初值 `0xFF`，严格 `<` 才更新，因此平局保留 castle id 最小者；
- 6058 会把 source 城自己算进去（距离 0），这是原版行为，不是 bug。

C 移植：

```c
int scenario_castle_distance(const Scenario *sc, int from, int to);
bool scenario_castle_distance_matrix(const Scenario *sc, uint8_t *out,
                                     int out_rows, int out_cols);
int scenario_nearest_friendly_castle(const Scenario *sc, int faction, int source);
int scenario_nearest_enemy_castle(const Scenario *sc, int faction, int source);
```

边界差异：原版各访问器没有统一的越界检查（`30FE` 直接读
`matrix[row*39+col]`）；C 侧对非法 id 统一返回 `0xFF` / `-1`。正常 39 城
数据上二者一致。

### 11.4 `0x22856` 邻接目标选择（B 级）

```text
if 5E1A(actor) == 0 or 0x920C == -1 or 0x920E == -1 or 0x9210 == -1
   or actor == 0x920C or 0x9212 == -1: return -1

d1 = matrix[actor][0x920C]
d2 = matrix[actor][0x920E]
best_ref = (d2 <= d1) ? 0x920E : 0x920C     // 平局取 B
best_dist = min(d1, d2)
best = (officers=5E1A(actor), dist=best_dist, ratio=0x9216)

for slot 0..6:
    cand = 20C6(actor, slot)
    if cand == -1: break
    owner = 21A8(cand)
    if owner != 0x9210 and owner != -1: continue
    officers = 5E1A(cand)
    if officers >= 15: continue
    dist = matrix[cand][best_ref]
    ratio = 5BC8(71B8(cand), 7350(owner, 0x9212, cand)) & 0xFF
    if (dist, officers, ratio) < (best_dist, best_officers, best_ratio):
        best = cand
return best or -1
```

`5BC8(a,b)` 实际公式为 `(a * 100) / (a + b)`（`a=b=0` 时为 50；详见 §12 V13 勘误）。
`0x226E0` 的初值以 `5BC8(value, cost)` 调用，候选处先压成本、再压价值，
因此 `a` 是 value，`b` 是 cost；结果为 $0 \sim 100$ 的 ROI 效能得分。
选择器取字典序最小，平局不替换。

C 接口：

```c
int ai_choose_adjacent_target_22856(const Scenario *sc, int castle_id,
                                    int own_faction, int ref_castle_a,
                                    int ref_castle_b, int route_source,
                                    int current_ratio,
                                    AiTargetScoreFn score_fn, void *user,
                                    AiAdjacentTarget *out);
```

- `score_fn == NULL` 时候选沿用当前 ratio，评分不参与平局；
- `7350` 路径成本与 `71B8` 城价值**没有**在 C 侧重写，避免把未确认模型
  冒充原版；
- 该函数**未**接入 `ai_run_turn()`；现有进攻逻辑仍是 C 级启发式。

## 13. 100% 完整战略与内政决策管线闭环 (0x22D82, 31CA:0A22, 0x2303C 六路内政)

### 13.1 六路内政核心算法与数值模型

在 `Main.exe` 文件偏移 `0x12aee`（运行时 `0x2303c`）处确立了六路内政的统一调度与资源结算公式：

1. **投入点数结算**：
   $$di = \min\left(\lfloor\text{castle\_gold} / 50\rfloor, \min(10, \lfloor\text{general\_stat} / 10\rfloor)\right)$$
   以 50 资金作为一个投入基准点，且受限于执行武将的能力评级（0~10）。
2. **随机波动增益**：
   $$\Delta = (\text{rand}() \bmod di) + 1$$
3. **六路内政分支实装**（调用点 `0x12c8b`、`0x12cf2`、`0x12e21`、`0x12f9b`、`0x13038`、`0x130d9`）：
   - **Branch 0: 施赈关怀 / 救济民忠**（`0x12c48` / `31CA:044A`）：民忠 $< 100$ 时触发，民忠增加 $\Delta$，扣除金钱 $di \times 50$。
   - **Branch 1: 城防修缮 / 巡查修筑**（`0x12c9c` / `31CA:0458`）：城防 $< 1000$ 时触发，城郭耐久增加 $\Delta \times 10$，扣除金钱 $di \times 50$。
   - **Branch 2: 产业开垦 / 商业开发**（`0x12d02` / `31CA:0474`）：石高增加 $\Delta \times 20$，扣除金钱 $di \times 50$。
   - **Branch 3: 士气演练 / 训练军备**（`0x12f00` / `31CA:0FFC`）：训练/士气 $< 100$ 时触发，士气增加 $\Delta$，扣除兵粮 $di \times 20$。
   - **Branch 4: 征兵招募**（`0x12fb0` / `31CA:100A`）：驻军未达人口上限时触发，兵力增加 $\Delta \times 15$，扣除金钱与兵粮。
   - **Branch 5: 赏赐武将**（`0x13050` / `31CA:145A`）：城内有忠诚度不满 100 的武将时触发，忠诚度增加 $\Delta$，扣除金钱 50。

### 13.2 调兵执行器 0x22D82 与 31CA:0A22 行军逻辑
